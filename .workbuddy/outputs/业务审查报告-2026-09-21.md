# docker-db-auto-backup 业务与备份流程审查报告

- 审查日期：2026-09-21
- 审查范围：`main.go` / `backup.go` / `docker.go` / `provider.go` / `validate.go` / `notify.go` / `kopia.go` / `compress.go` / `image.go` / `tree.go` / `config.go`，以及 `Dockerfile`、`docker-compose.yml`、`README.md`
- 代码规模：约 1200 行 Go（不含测试），单静态二进制 CLI，无子命令、无持久化状态

---

## 一、总体结论

产品定位清晰（Docker 宿主侧数据库容器自动逻辑备份 + 可选异地快照），主干链路"发现容器 → 识别镜像 → 选择 provider → exec dump → 压缩 → 校验 → 落盘 → 异地快照 → 通知 → 清理"是**完整且自洽**的，工程细节（临时文件 + rename 原子落盘、并发 worker 池、exec 复用缓存、压缩与 Kopia 互斥）都做得比较到位。

但存在一个**结构性缺陷**：错误处理模型是"全有或全无"（all-or-nothing）。任何单个容器的失败都会中断整条链路，导致其余成功产出的备份既不推送异地、也不发通知、也不做保留清理；在调度模式下还会 `os.Exit(1)` 直接终止进程，本次窗口永久丢失。结合"不检查 dump 进程退出码""Redis 使用同步 SAVE""无超时与重试"三点，当前实现在**生产环境下的备份完整性保证不足**——最坏情况是运维以为每天都有备份，实际连续多天静默丢失。

**优先级定义**
| 级别 | 含义 |
|---|---|
| **P0** | 存在备份静默丢失、数据损坏或源库生产事故风险，建议立即修复 |
| **P1** | 影响可靠性、成本可控性或可运维性，建议本迭代修复 |
| **P2** | 影响体验、扩展性或诊断效率，建议排期处理 |

## 二、A 类：需要优化的环节

### A1. 部分失败阻断全局，成功产出既不快照也不通知 —— P0
- **现状**：`backup.go:90-95`，`if len(errs) > 0` 直接 `return`，跳过其后的 Kopia 快照（97-118 行）、通知（130-134 行）、保留清理（136-138 行）；且只上报 `errs[0]`，其余错误被丢弃。
- **影响**：10 个数据库容器中 1 个失败 → 另外 9 个成功的备份**不会进入异地仓库**，本地也不会收到任何通知。异地备份的连续性被打断，而运维完全无感知。这是本产品最严重的逻辑缺陷。
- **建议**：引入三态结果（全部成功 / 部分失败 / 全部失败）。部分失败时：仍然执行 Kopia 快照、仍然发送通知，但通知标题与 Healthchecks 正文明确列出失败容器清单及原因；仅当 `全部失败` 且 `results 为空` 时才判为整体失败。错误信息用 `errors.Join` 聚合而非只取首个。

### A2. 无备份重试与单任务超时 —— P0
- **现状**：`writeBackup()`（`backup.go:213`）一次执行失败即判定失败；全局 `ctx` 仅受 SIGTERM/SIGINT 控制（`main.go:17`），无 per-container 超时。
- **影响**：数据库容器恰好在备份瞬间重启、连接数打满、或 `pg_dump` 遭遇长事务锁等待时，单次抖动即造成当天备份缺失；若 dump 进程挂起，整个备份流程会无限期阻塞，后续所有调度周期全部堆积。
- **建议**：为每个 `writeBackup` 增加可配超时（默认 30~60 分钟，环境变量 `BACKUP_TIMEOUT_MINUTES`），并对**非内容类错误**（exec 创建失败、连接类错误）做 2 次指数退避重试；对"校验失败/空文件"这类确定性错误不重试，避免放大问题。

### A3. 并发度默认取 CPU 核数，未考虑源库承载 —— P1
- **现状**：`config.go:49`，`workers: envInt("BACKUP_WORKERS", runtime.NumCPU())`。
- **影响**：备份瓶颈在**数据库容器侧 CPU/IO 与磁盘**，不在备份容器。默认 `NumCPU` 并发会让多个 `mysqldump --all-databases`（会持长事务、对 MyISAM 加全局锁）同时冲击线上库；同时 N 路并发写盘也让备份目录 IO 打满。
- **建议**：默认值改为 `min(NumCPU, 2)` 或直接定为 `2`，并在 README 中显式说明该变量（**当前 `BACKUP_WORKERS` 完全未出现在 README 环境变量表中**，属文档缺失）。

### A4. 校验阶段对 plain 备份也全量重读，IO 翻倍 —— P1
- **现状**：`validate.go:36-68`，为取尾部 `tailBuffLen`（64KB）而从头到尾 `Read` 整个流；`plain` 模式下没有任何解压 CRC 收益，纯粹是额外一次全量读盘。
- **影响**：大库（数十 GB）场景下，校验耗时与磁盘读 IO 直接翻倍，与 A3 的并发叠加后可能把备份窗口拖到小时级。
- **建议**：对 `plain` 模式改用 `Seek` —— 头部读 `headBuffLen`，尾部 `Seek(-tailBuffLen, io.SeekEnd)` 读 `tailBuffLen`，不再全量遍历；仅对 `gzip/xz/bz2` 保留全量解压（此时 CRC 校验才有价值）。

### A5. 单库模式内各库串行备份，耗时随库数线性增长 —— P2
- **现状**：`backup.go:166-184`，对 `provider.singleDB()` 返回的库列表是一个 `for` 循环内串行 `writeBackup`，未纳入外层 worker 池。
- **影响**：一个 40 库的 PostgreSQL 实例，单库模式耗时约为全库模式的数十倍，容易越过调度间隔，进而触发"重叠运行"（见 B3）。
- **建议**：把（容器, 库）作为最小调度单元放入统一的 worker 池，`BACKUP_WORKERS` 作为全局并发上限。

### A6. 多 worker 并发下进度条交错输出 —— P2
- **现状**：`backup.go:234-240`，每个 `writeBackup` 在 `showProgress` 时 `progressbar.NewOptions64(-1)` 并写 stdout；`progressbar` 库通过 `\r` 移动光标，多 goroutine 并发写同一终端时互相覆盖。
- **影响**：容器环境下 `docker logs` 输出混乱、难以解析；进度条只显示字节数无总量，信息量低。
- **建议**：并发数 > 1 时关闭交互式进度条，改为每个任务一行结构化输出（容器名、库名、体积、耗时）；或为每个 worker 分配固定行号区域。

### A7. 通知内容缺少可判断健康度的关键指标 —— P2
- **现状**：`tree.go` 仅输出"容器名 + 库名"的嵌套列表；`backup.go:132` 的通知正文只有容器计数与耗时。
- **影响**：运维收到通知后无法判断"某个库是不是变成 0 字节""备份体积是否突降（可能意味着 dump 异常）""Kopia 是否真的推成功了"。
- **建议**：通知中补充每库体积、总字节数、失败明细、Kopia 快照 ID 与耗时；异常体积波动（较昨日 ±50%）时给出提示。

### A8. "发现 N 个容器"与实际备份数口径不一致 —— P2
- **现状**：`backup.go:39` 打印的是宿主上**全部**容器数，`backup.go:126` 打印的是**被识别为数据库**的容器数；识别失败（`getBackupProvider` 返回 nil）时 `backupContainer` 返回 `(nil, nil)`，无任何日志。
- **影响**：日志显示"发现 30 个容器…成功备份 3 个"，运维无法判断另外 27 个是"正常非数据库"还是"数据库但未被识别"，漏备份风险被掩盖。
- **建议**：启动时打印"识别到 M 个数据库容器（跳过 K 个非数据库容器）"，并对疑似数据库（镜像名含 `postgres|mysql|mariadb|redis|valkey|mongo` 等关键词但未匹配上 pattern）的容器输出显式警告。

## 三、B 类：建议新增的功能

### B1. CLI 子命令（手动触发 / 列表 / 校验 / 状态） —— P1
- **理由**：当前**完全没有子命令**，一切行为靠环境变量驱动。要手动跑一次必须改 `SCHEDULE=""` 再重启容器；无法列出历史备份、无法对已有备份做离线校验、无法查看上次运行状态。这直接导致"备份是否真的可用"无法被验证。
- **建议**：至少提供 `run`（立即执行一次，不改配置）、`list [--date]`（列出备份清单与体积）、`verify --date`（离线重跑校验 + 校验和比对）、`status`（上次成功时间/失败数/下次计划时间）。

### B2. 备份清单 manifest（含 sha256 与元数据） —— P1
- **理由**：目前备份目录只有裸文件，没有任何元数据。无法追溯"这次备份是什么时候、由哪个容器、哪个 provider、多大、校验和是多少"。
- **建议**：每次备份在日期目录写入 `manifest.json`：`{run_at, duration, containers[{name, image, provider, files[{path, size, sha256}]}], kopia_snapshot_id}`。这是 B1 `verify`、A7 体积波动检测、以及合规审计的共同基础。

### B3. 重叠运行保护（单实例锁） —— P1
- **理由**：`runScheduled`（`main.go:48-61`）是 `for { 等待 → backup() }` 的串行循环，但如果单次备份耗时超过调度间隔（大库 + A5 串行单库模式极易发生），下轮 `backup()` 会在上一轮结束后立即补跑；若将来改为并发或引入 `SCHEDULE` 短周期，则可能两次 backup 同时写同一日期目录。且当前串行循环意味着**超时一次，后续所有周期全部顺延漂移**。
- **建议**：在 `BACKUP_DIR` 下创建 `.lock` 文件锁（flock），检测到已有运行实例时记录告警并跳过本轮；同时支持"错过窗口是否补跑"的可配策略。

### B4. 备份前磁盘空间预检 —— P1
- **理由**：`writeBackup` 先写临时文件再 rename，空间不足时会在写了一半才失败，留下残缺状态；且失败信息不直观。
- **建议**：备份开始前用 `unix.Statfs` 检查 `BACKUP_DIR` 可用空间，若低于"上次总备份体积 × 安全系数（如 1.2）"则提前失败并发送明确告警。需要 B2 的 manifest 提供历史体积基线。

### B5. 容器级包含 / 排除清单 —— P1
- **理由**：当前是"扫描所有运行中容器，识别即备份"，无法排除某个测试库容器，也无法只备份打了特定 label 的容器。生产环境这是刚需。
- **建议**：支持 `BACKUP_INCLUDE_LABELS`（如 `backup=true`，优先级最高）、`BACKUP_EXCLUDE_CONTAINERS`（容器名逗号分隔）、`BACKUP_INCLUDE_CONTAINERS`（白名单模式）。

### B6. Kopia 保留策略、维护任务与快照打标 —— P1
- **理由**：`kopia.go` 只实现了 `repository status/connect/create`、`policy set --compression`、`snapshot create`。**没有 retention 策略、没有 `snapshot expire`、没有 `maintenance run`**。本地 `BACKUP_RETENTION_DAYS` 删掉旧目录，远端快照却只增不减，存储成本持续线性上涨；长时间不跑 maintenance 也会影响仓库性能与可靠性。
- **建议**：新增 `KOPIA_RETENTION_*`（按时间/数量保留）映射到 `policy set --global --keep-latest/--keep-daily/...`，并在快照成功后周期性执行 `maintenance run --full`（可按周/按 N 次快照触发）；快照命令补充 `--description` 与自定义 tag，便于远端定位某次备份。

### B7. 恢复演练（restore drill） —— P1
- **理由**：`BACKUP_VALIDATE` 目前只是**格式校验**（检查 dump 头尾标识与压缩流 CRC），不是**可恢复性校验**。逻辑备份最常见的失败模式恰恰是"文件看起来完整、但恢复时报错"（扩展版本不匹配、search_path 问题——README 第 118-139 行已承认 TimescaleDB / VectorChord 存在这类坑）。
- **建议**：新增可选 `BACKUP_RESTORE_DRILL=true`：启动一次性临时容器（同镜像），导入 dump，验证关键表可查询，结束后销毁并上报结果。可与 B1 `verify` 共享实现。

### B8. 结构化日志与可选监控指标 —— P2
- **理由**：当前全部是 `fmt.Println/Printf`，无级别、无字段、无时间戳（依赖 Docker 自身时间戳）。无法接入日志系统，也无法回答"哪一步慢""哪个库反复失败"。
- **建议**：改用 `log/slog` 输出 JSON 日志（字段：container、provider、db、size、duration、exit_code、error）；可选暴露 Prometheus 指标（最后成功时间戳、备份总字节、失败计数、各阶段耗时）。

### B9. 备份集异常检测（容器数骤减 / 体积骤变） —— P2
- **理由**：数据库容器因 OOM 或健康检查失败而停止时，`ContainerListOptions{}`（`docker.go:38`，默认只列 running）会静默跳过它，备份数量减少但流程仍报"成功"。这是最隐蔽的一类丢备份。
- **建议**：基于 B2 manifest 对比上一次运行：数据库容器数量减少、或某容器备份体积较昨日波动超过阈值（如 ±50%）时，在通知与 Healthchecks 中标记为 `WARN`。

### B10. 镜像识别的覆盖面与可配置扩展 —— P2
- **理由**：`provider.go:183-216` 的 pattern 是硬编码的。缺少 `bitnami/postgresql`、`bitnami/mariadb`、`bitnami/redis`、`zabbix/zabbix-server-mysql`、CNPG / Crunchy 等常见发行版；用户自建镜像无法接入。
- **建议**：保留内置 pattern，同时支持 `BACKUP_IMAGE_PATTERNS_FILE`（YAML：镜像 pattern → provider → 自定义 dump 命令），让用户无需 fork 即可扩展。

## 四、C 类：应当修改调整的部分

### C1. 调度模式下备份失败直接 `os.Exit(1)` —— P0
- **现状**：`main.go:57-60`，`runScheduled` 内 `backup()` 返回错误即 `os.Exit(1)`。
- **影响**：容器 `restart: unless-stopped` 会重启进程，但 cron 已错过本次窗口，这天的备份**永久丢失**；若失败原因持续存在，进程陷入 crash-restart 循环，后续所有备份全部停滞。
- **修改**：调度模式下的单次失败不应终止进程——记录错误、发送 Healthchecks `/fail`（带上原因）、继续等待下一个周期。仅配置类致命错误（如 Docker socket 不可用）才退出。

### C2. `writeBackup` 不检查 dump 进程的退出码，且丢弃 stderr —— P0
- **现状**：`backup.go:221-253`：`_, attach, err := dc.startExec(...)` —— 用 `_` 丢弃了 `execID`，**从未调用 `ExecInspect` 检查 ExitCode**；同时 `stdcopy.StdCopy(writer, io.Discard, attach.Reader)` 把 stderr 写入 `io.Discard`。注意 `docker.go:143-149` 的 `execCollect` 是检查了退出码的，两者行为不一致。
- **影响**：`pg_dump` 因权限不足、磁盘满、版本不匹配而中途退出（exit≠0）时，程序收不到任何信号；stdout 的部分输出仍被写入文件，只要尾部恰好包含 "dump complete" 就会通过校验，最终产出一个**看起来合法但实际残缺的备份**。同时所有错误现场被丢弃，事后无法排障。
- **修改**：保留 `execID`，`StdCopy` 后调用 `ExecInspect`，`ExitCode != 0` 时判为失败；把 stderr 收集到缓冲区（限制大小）并附在错误信息中。

### C3. Redis 使用同步 `SAVE`，且硬编码 `/data/dump.rdb` —— P0
- **现状**：`provider.go:88`：`sh -c "redis-cli SAVE > /dev/null && cat /data/dump.rdb"`。
- **影响**：(1) `SAVE` 是**同步阻塞**命令，会阻塞 Redis 主线程直到 RDB 落盘完成，生产大实例可能数十秒到分钟级，期间所有客户端请求挂起——这在生产环境属于事故级操作，与"备份不应影响业务"的基本原则冲突。(2) 硬编码 `/data/dump.rdb`，若容器通过 `CONFIG SET dir/dbfilename` 或启动参数自定义了 RDB 路径，备份会失败或备份到错误文件。(3) `SAVE` 会**覆盖源容器内的 dump.rdb**，属于对源容器的副作用写入。
- **修改**：改用 `BGSAVE` + 轮询 `INFO persistence` 的 `rdb_bgsave_in_progress` 直到完成，再 `cat` 通过 `CONFIG GET dir` / `CONFIG GET dbfilename` 动态获取的路径；全部失败时再回退到 `SAVE`。

### C4. MySQL 凭据以 `$VAR` 字面量进入 shell，存在挂死风险 —— P0
- **现状**：`provider.go:173-181` 返回字符串 `-p$MARIADB_ROOT_PASSWORD`（**字面量**，由容器内 shell 展开），命令为 `bash -c "mysqldump -p$MARIADB_ROOT_PASSWORD --all-databases"`（`provider.go:76`）。
- **影响**：(1) 若容器内不存在该环境变量（使用 secret file、`MYSQL_RANDOM_ROOT_PASSWORD=yes`、或变量名不同），命令退化为 `mysqldump -p --all-databases`，`mysqldump` 会**交互式等待密码输入**——叠加 C1/A2 的"无超时"，整个备份永久挂死。(2) 密码以命令行参数形式出现在容器进程列表中（`ps` 可见）。
- **修改**：通过 `startExec` 的 `env` 参数注入 `MYSQL_PWD`（MySQL 客户端原生支持），命令行只保留 `-u root`；或在拼接前显式校验容器内该变量确实存在，不存在则立即失败而非挂起。

### C5. 凭据识别面过窄 —— P1
- **现状**：PostgreSQL 仅读 `POSTGRES_USER`（`provider.go:166`），默认 `postgres`；MySQL 仅认 `MARIADB_ROOT_PASSWORD` / `MYSQL_ROOT_PASSWORD`（`provider.go:173`）。
- **影响**：linuxserver 系列（用 `PGUSER`/`MYSQL_USER`）、CloudNativePG、使用非 root 备份账号、或使用 socket/peer 认证的容器全部无法备份；且**不支持自定义备份专用账号**（生产上用 root 做备份本身也是权限风险）。
- **修改**：读取顺序扩展为 `POSTGRES_USER → PGUSER → 容器 label 覆盖`；MySQL 扩展为 `MARIADB_ROOT_PASSWORD → MYSQL_ROOT_PASSWORD → MYSQL_PWD → 备份专用用户（新增 `BACKUP_MYSQL_USER` / `BACKUP_MYSQL_PASSWORD`，未设置时回落 root）`。

### C6. 镜像识别仅依赖 `RepoTags`，无兜底 —— P1
- **现状**：`docker.go:57-61`，`ImageInspect(inspect.Container.Config.Image)` 后只取 `imgInspect.RepoTags`。
- **影响**：以 digest 启动、镜像被重新 tag 导致原 tag 悬空、或本地构建镜像时，`RepoTags` 可能为空 → `imageNamesFromTags` 返回空数组 → `getBackupProvider` 返回 `nil` → **容器被静默跳过**，不备份、不告警（与 A8 叠加）。
- **修改**：增加兜底链：`RepoTags → RepoDigests（取仓库名）→ Config.Image 字符串 → 容器 labels（如 `com.docker.compose.image` / 自定义 `backup.provider`）`。任一兜底命中应在日志中标注来源。

### C7. 残留临时文件会被 Kopia 快照进仓库 —— P1
- **现状**：`writeBackup` 用 `os.CreateTemp(filepath.Dir(backupFile), ".auto-backup-")`（`backup.go:214`），与目标文件同目录；进程被 kill 时 `defer os.Remove` 不会执行。
- **影响**：中断残留的 `.auto-backup-*` 永久留在备份目录，会被 `kopia.snapshotCreate(ctx, backupBase)` 一并推到远端，污染仓库、浪费存储，且让"某天的备份内容"变得不确定。
- **修改**：启动时扫描 `BACKUP_DIR` 清理超过一定时间的 `.auto-backup-*`；或把临时文件放到 `BACKUP_DIR/.tmp/`（并在 Kopia 快照时排除该目录）。

### C8. 时区依赖隐式，备份目录日期可能差一天 —— P1
- **现状**：`dateDir = runAt.Format("2006-01-02")`（`backup.go:37`）与 `cleanOldBackups` 的 `time.ParseInLocation(..., time.Local)`（`backup.go:300`）都依赖进程本地时区；`Dockerfile:34` 设了 `TZ=Asia/Shanghai`，但用户若挂载自己的 compose 而未设 `TZ`，容器默认为 UTC。
- **影响**：北京时间 00:00 触发的备份在 UTC 容器里会落到**前一天**的日期目录，保留期计算随之偏移一天，跨时区部署时备份目录与用户预期不一致。
- **修改**：新增 `TZ` 环境变量的显式说明（README 当前未提），并在启动日志打印当前时区与"下次运行时间（本地）"；可选支持 `BACKUP_TZ` 独立于系统时区。

### C9. MySQL 单库模式丢弃系统库，与 PostgreSQL 行为不一致 —— P2
- **现状**：`mysqlSingleDB`（`provider.go:155-157`）遇到系统库直接 `continue`；而 `psqlSingleDB`（`provider.go:105-120`）会把系统库写入 `system/` 目录并额外生成 `globals.sql`。
- **影响**：MySQL 的 `mysql` 库（用户与权限定义）在单库模式下**完全不备份**，恢复到新实例后需要手工重建账号；两端行为不一致也容易让使用者误判。
- **修改**：与 PostgreSQL 对齐——MySQL 系统库同样输出到 `system/` 子目录（可选择通过开关关闭）。

### C10. Healthchecks 失败心跳逻辑重复且信息为空 —— P2
- **现状**：`backup.go` 中 4 处重复的 `if hcURL != "" { hcPing(hcURL+"/fail", "") }`（92、100、106、112 行），且 fail 心跳的 body 为空字符串。
- **影响**：Healthchecks 支持把 POST body 作为失败日志展示，当前实现看不到任何失败原因；重复代码也容易在新增失败路径时遗漏。
- **修改**：抽成统一的 `func fail(ctx, reason string)`（或用 defer 统一出口），并把聚合后的错误原因作为 body 发送。

### C11. 单库模式回退未在结果中体现 —— P2
- **现状**：`backup.go:163-165`，`provider.singleDB` 失败时打印警告并回退到全库模式，但返回的 `backupResult` 中 `dbs` 为 nil，与"provider 本就不支持单库"的场景无法区分。
- **影响**：通知中看不出这次是全库备份还是单库备份（配置 `SINGLE_DB_MODE=true` 的用户会误以为逐库备份成功了）。
- **修改**：`backupResult` 增加 `mode` 字段（`single` / `full` / `full-fallback`），在通知与日志中体现。

### C12. 数据库名未做路径安全校验 —— P2
- **现状**：`filepath.Join(dbDir, fmt.Sprintf("%s.%s%s", db.name, ...))`（`backup.go:176`）直接使用数据库名作为文件名。
- **影响**：PostgreSQL 允许通过双引号创建含 `/` 或 `..` 的数据库名，理论上可造成路径穿越写入备份目录之外（风险等级低，因为攻击者需先有建库权限）。
- **修改**：对 `db.name` 做白名单校验（仅允许 `A-Za-z0-9_-.`），非法字符做转义或拒绝并告警。

### 行为变更（升级需注意）

1. **部分失败不再返回非零码**：只有"无任何容器产出备份"才算整体失败。若原有监控依赖退出码判断，请改为读取 `manifest.json` 的 `status`，或监控 Prometheus 的 `db_backup_last_status`。
2. **Redis 不再执行同步 `SAVE`**，RDB 路径改为动态获取；备份对主线程无阻塞。
3. **MySQL 密码通过 `MYSQL_PWD` 注入**，命令行中不再出现 `-p`；容器内若找不到任何密码变量会直接报错而非挂起。
4. **MySQL 单库模式现在会备份系统库**（落到 `system/` 目录），与 PostgreSQL 行为对齐。
5. **备份目录新增 `.tmp/` 与 `.backup.lock`**，前者不会进入 Kopia 快照；升级后旧的残留临时文件会在首次运行时自动清理。
6. **日期目录依赖时区**，务必设置 `TZ` 或 `BACKUP_TZ`。
