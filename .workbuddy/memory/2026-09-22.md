## CI e2e-test 失败根因与修复（提交 d0e3ab7）
- 现象：push 46eefd1 后 CI 的 `e2e-test` job 在 "Run e2e test" 步骤失败（lint / test -race 均通过）。
- 根因：`validate.go` 新增的 RDB 校验要求「末字节 == 0xFF」。真实 Redis 在 `rdbchecksum=yes`（默认）时文件末尾是 `0xFF` + **8 字节 CRC64**，末字节不是 0xFF → Redis 备份一律被判"截断"丢弃 → 状态 partial → 脚本 `assert_four_files` 报 missing rdb 退出 1。
- 单测没发现是因为 mock 的 RDB 数据是我手工构造的、恰好以 0xFF 结尾（自证式测试）。已把 mock 改为真实布局 `...\xff + 8 字节`，并补充"带/不带 CRC64"两组正例 + 截断负例。
- 修复：`rdbHasEOFMarker()` 按「倒数第 9 字节（带 CRC64）/ 末字节（无校验和）」两种布局查找 0xFF。

## 生产日志（01:25 调度轮）暴露的第二类失败：MySQL 系统库 LOCK TABLES
- 日志里 8 个失败 = 6 个 valkey（上面那个 RDB 0xFF 原因，**同一根因**）+ 2 个 MariaDB 系统库（**新原因**）：
  - `mariadb/information_schema`：退出码 2，`1044 Access denied ... when using LOCK TABLES`
  - `mariadb/performance_schema`：退出码 2，`1142 SELECT, LOCK TABLES command denied ... performance_schema.accounts`
- 根因：单库模式（SINGLE_DB_MODE）用 `INFORMATION_SCHEMA.SCHEMATA` 列出全部库，把 information_schema / performance_schema 也逐个 dump；这两者是内存虚拟表，mysqldump 自身的 `--all-databases` 也会跳过。
- 修复（提交 `e40fc1b`）：新增 `nonDumpableMySQLSchemas`，在 `mysqlSingleDB` 中跳过这两个库；`mysql` / `sys` 仍照常备份（恢复实例需要账号与权限）。mock 的库列表也改成真实集合以覆盖该分支。

## SQLite 备份支持：可行性分析 + 详细设计（待实现）
- 需求：为内嵌 SQLite 的应用容器（Home Assistant / Vaultwarden / navidrome / FreshRSS / PhotoPrism）加备份。用户选定：**默认 SQL dump 格式，先出详细设计再动手**。
- 结论：**可行，且不需要改 `backup.go` 的落盘主链路**。所有 provider 都是「容器内 exec → stdout 流 → 压缩 → 校验 → rename」，Redis 的 `sh -c "... cat dump.rdb"` 已证明二进制流可走同一管道。
- 三个差异：(1) SQLite 无独立官方镜像，`patterns` 匹配无意义，只能靠 `backup.provider=sqlite` 标签（已有机制，优先级最高，新增同名 provider 即自动生效）；(2) 这类应用镜像多不带 `sqlite3` CLI，需用 `dc.hasBinary` 探测；(3) **一致性是核心风险**——直接 cp 正在写入的 .db 会丢未 checkpoint 的 WAL。
- 关键设计决策：**`.dump` 是逐表顺序读，autocommit 下不保证跨表单一快照**，故不能直打源库。改为「先 `sqlite3 src ".backup /tmp/x.db"`（官方 backup API，原子快照、含 WAL）→ 再 `.dump` 该快照 → printf 一行 `-- SQLite dump complete`」。最后这行既是合法 SQL 注释，又能复用 `validate.go` 中 sql 分支要求的 "dump complete" 尾部标记，无需改校验代码。
- 其他决策：`forceSingle` 字段让 SQLite 始终按库拆分输出；无 CLI 时**默认报错**（符合项目「宁可失败也不产出可疑备份」原则），需 `backup.sqlite.fallback=copy` 显式开启降级（fileExt 改 db + 新增 `SQLite format 3\0` 魔数校验）；路径用 `backup.sqlite.path` 标签，容器内 glob 展开。
- 不接入恢复演练：演练容器用源镜像，而这些镜像恰恰没有 sqlite3 CLI；在备份容器内解析需引入 cgo（mattn/go-sqlite3），破坏静态编译。
- 产出：`docs/sqlite-backup-design.md`（含现状分析、3 个约束、4 个决策、按文件的改动清单、测试方案、风险表）。约 200 行实现 + 150 行测试，涉及 5 个源文件。

## SQLite 设计修订：实测"目标容器普遍无 sqlite3" → 改默认注入
- 用户实测确认 Home Assistant / Vaultwarden / navidrome / FreshRSS 等应用镜像几乎都不带 `sqlite3` CLI。原设计"无 CLI 默认报错"在真实场景会让 SQLite 几乎全失败，故推翻该默认。
- 新默认：**备份镜像自带完全静态链接的 `sqlite3`**（Dockerfile 新增 `gcc -static` 编译官方 amalgamation 阶段），每次备份前 `sqliteEnsureCLI` 用 `docker cp`（`CopyToContainer`）注入目标 `/tmp/auto-backup-sqlite3`；目标已有时直接复用省一次拷贝。静态=跨 libc（备份镜像 Alpine/musl，目标多为 Debian/glibc）。
- 仍用「先 `.backup`（原子快照、含 WAL 已提交）→ 再 `.dump` → printf `-- SQLite dump complete`」保证**完整且跨表一致**，直接回答"能否完整备份"=能。`.backup` 把 `-wal` 已提交事务 checkpoint 进快照，故 WAL 模式并发写入也不丢。
- 注入失败（目标无 /tmp、只读根、CopyToContainer 报错）才转 `permanent` 错误；`backup.sqlite.fallback=copy` 仍是显式原始拷贝兜底（此时尽量带上 `-wal`/`-shm`）。
- 已更新 `docs/sqlite-backup-design.md` §1/§3.2/§4 决策1&3/§5.1/§5.3/§5.6(Dockerfile)/§7/§8/§9，新增 `copyFileToContainer`、`sqliteEnsureCLI` 两函数、Dockerfile 静态 sqlite3 构建阶段；仍不改动落盘主链路。涉及 6 个源文件。
